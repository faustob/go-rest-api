**Auto-fixed during review (8):**
- qr-preserves-behavior (`cmd/server.go`): initOtel is called AFTER the router and all middleware (including saturationMiddleware/authTelemetryMiddleware) are constructed, but that is fine; the real defect is that initOtel and its deferred shutdown are placed correctly before StartServer. However, the deferred shutdownOtel() will never run because api.StartServer blocks until the process is killed, and on SIGTERM the deferred call is bypassed — telemetry buffered in the batch/periodic exporters is lost on shutdown.
- qr-preserves-behavior (`cmd/server.go`): The router is wrapped with otelhttp.NewHandler at the outermost layer, which means the chi RouteContext is not yet populated when otelhttp runs; but saturationMiddleware runs inside chi so RouteContext is available there. This wrapping order is acceptable, but the otelhttp span name uses a static serviceName for every route, producing a single non-descriptive span name for all requests.
- qr-preserves-behavior (`cmd/auth_middleware.go`): authTelemetryMiddleware is registered on the protected router AFTER jwtValidator.Middleware (protectedRouter.Use(jwtValidator.Middleware) then protectedRouter.Use(authTelemetryMiddleware)), so it runs INSIDE the validator. A rejected request never reaches authTelemetryMiddleware, so denials are never recorded and only allowed requests are counted — the auth.attempts denial path is dead.
- qr-preserves-behavior (`cmd/routes_telemetry.go`): withRouteSpan starts a child span with a context (ctx) that is discarded (assigned to _), so the span is never attached to the request context passed downstream; child spans created in handlers will not be parented to this span, breaking trace correlation.
- qr-preserves-behavior (`cmd/server.go`): initOtel() is called after the router and all middleware/routes are constructed, but that is fine ordering-wise; the real problem is that initOtel runs immediately before StartServer, and shutdownOtel is deferred inside main() — but StartServer blocks until the server stops, so the deferred shutdown does run. However, otelHandler wraps the router but the router's own saturationMiddleware and per-request handlers still work. This is acceptable.
- qr-preserves-behavior (`cmd/auth_middleware.go`): authTelemetryMiddleware relies on the JWT validator middleware calling next.ServeHTTP; but it is registered AFTER jwtValidator.Middleware in the protected group, so when the JWT middleware denies a request it writes 401/403 and does NOT call next — meaning authTelemetryMiddleware never runs for denials and only ever records "allowed". Denials are never counted.
- general (`cmd/routes_telemetry.go`): withRouteSpan discards the span-bearing context (ctx is assigned to _ and never propagated), so any child spans or metric exemplars created downstream will not be linked to this span; the span is effectively orphaned from the request handler's work.
- qr-not-a-noop (`cmd/server.go`): otelhttp.NewHandler wraps the router but the second argument is serviceName ("change-me"), which otelhttp uses as the span operation name for every request, producing a single fixed span name rather than a route-based one; combined with the router being wrapped at the outermost layer this is fine functionally but the constant operation name is a misuse.
**Outstanding (4):**
- ⚠ qr-endpoint-env-driven (`cmd/otel.go`:4): Hardcoded OTLP endpoint "localhost:4317" — wrong in every real deployment. — _Read the endpoint from OTEL_EXPORTER_OTLP_ENDPOINT / config instead of a literal._
- ⛔ qr-not-a-noop (`cmd/server.go`): otelhttp.NewHandler wraps the router at the outermost layer, but the metric instruments in telemetry.go and the spans in routes_telemetry.go are only invoked from saturationMiddleware, authTelemetryMiddleware, and withRouteSpan, none of which are ever registered onto the router or called by any handler. As a result the entire custom instrumentation (active_requests, auth.attempts, flow.outcomes, flow.duration, flow.validation.outcomes, route spans) never executes and emits nothing. — _Wire the new middleware into the chi router (e.g. router.Use(saturationMiddleware), protectedRouter.Use(authTelemetryMiddleware)) and call withRouteSpan inside the actual route handlers._
- ⛔ qr-preserves-behavior (`cmd/otel.go`): initOtel imports and uses "go.opentelemetry.io/otel/semconv/v1.26.0", but this package is not declared in go.mod's require block, so the build will fail to resolve the dependency. — _Add go.opentelemetry.io/otel/semconv (bundled with go.opentelemetry.io/otel) — it is part of the otel module already required, so verify the v1.26.0 subpackage path exists in v1.35.0 and adjust the import version accordingly._
- ⚠ qr-preserves-behavior (`cmd/auth_middleware.go`): authTelemetryMiddleware wraps the response with a statusRecorder whose WriteHeader captures the code, but handlers that never call WriteHeader (returning 200 implicitly) leave statusCode at the default http.StatusOK — this is fine, however denials produced by the JWT middleware writing 401/403 after this wrapper are correctly captured; the real concern is that if the wrapped chain never writes a status (streaming or hijacked responses), the default 200 causes a false "allowed" record. Given otelhttp sits above, hijacked connections would misreport auth outcome. — _Track whether WriteHeader was actually called and skip recording (or record an 'unknown' outcome) when no explicit status was written._
