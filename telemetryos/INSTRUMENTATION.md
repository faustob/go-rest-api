**Auto-fixed during review (7):**
- qr-not-a-noop (`pkg/telemetry/telemetry.go`): Instruments used by the middleware (requestDuration, requestOutcomeTotal, flowOutcomesTotal, flowEntryTotal, etc.) are package globals initialized only inside initInstruments(), which is called at the END of SetupOTelSDK. If SetupOTelSDK returns early on any exporter/resource error (e.g. otlptracegrpc.New or otlpmetricgrpc.New failing), main() panics — but even in normal flow the middleware dereferences these nil instruments. RequestTelemetryMiddleware calls flowOutcomesTotal.Add / requestDuration.Record with no nil-guard, so if instruments failed to initialize they are nil interfaces and will nil-panic on the first request.
- qr-preserves-behavior (`pkg/telemetry/telemetry.go`): statusRecorder implements Flush but does not implement http.Hijacker or io.ReaderFrom, so wrapping every response in RequestTelemetryMiddleware and AuthOutcomeMiddleware strips the Hijacker/ReaderFrom interfaces from the underlying ResponseWriter. Any handler relying on connection hijacking (e.g. websockets, SSE upgrades) or optimized sendfile will break, changing existing behavior. The comment claims it 'preserves the full contract' including Hijacker/ReaderFrom, but neither is implemented.
- general (`pkg/telemetry/telemetry.go`): AuthOutcomeMiddleware wraps the response in a second statusRecorder even though RequestTelemetryMiddleware already wrapped it, producing nested wrapping that further compounds the loss of Hijacker/ReaderFrom and double-buffers status tracking.
- general (`pkg/telemetry/telemetry.go`): The imports 'go.opentelemetry.io/otel/sdk/metric/metricdata' and 'go.opentelemetry.io/otel/metric/noop' are only kept alive with dummy _ references and serve no functional purpose, adding unnecessary dependencies.
- qr-preserves-behavior (`pkg/telemetry/telemetry.go`): The AuthOutcomeMiddleware and RequestTelemetryMiddleware both install/read the statusRecorder, but AuthOutcomeMiddleware writes through the recorder found in context while the JWT validator middleware runs BEFORE AuthOutcomeMiddleware in the chain and writes its 401/403 response directly to the raw ResponseWriter (or the RequestTelemetry recorder) — not through this middleware. Because AuthOutcomeMiddleware is registered after jwtValidator.Middleware, a denial short-circuits at the validator and never reaches AuthOutcomeMiddleware's ServeHTTP, so 'denied' auth outcomes are never recorded, making the auth SLI silently undercount denials.
- qr-preserves-behavior (`pkg/telemetry/telemetry.go`): statusRecorder no longer works transparently for handlers that write bodies: RequestTelemetryMiddleware installs rec, then AuthOutcomeMiddleware (when a recorder is in context) passes the same rec to next.ServeHTTP but passes the original request r whose context still points to the same rec, so downstream handlers using the recorder is fine; however the double-wrapping fallback path creates a second statusRecorder wrapping w rather than rec, so on the protected routes the response is written through the outer rec while the inner localRec's status is what's recorded — mismatched only in the fallback branch which is unreachable here.
- qr-preserves-behavior (`pkg/telemetry/telemetry.go`): SetupOTelSDK wraps otel.SetTracerProvider/SetMeterProvider in recover() guards claiming they can panic if a provider is already registered, but these functions do not panic on re-registration; the defensive recover is dead code and the misleading comments could mask real errors, though it does not itself break telemetry.
**Outstanding (3):**
- ⛔ qr-preserves-behavior (`pkg/telemetry/telemetry.go`): AuthOutcomeMiddleware reuses the statusRecorder installed by RequestTelemetryMiddleware but calls next.ServeHTTP(rec, r) with the original request r, not the request carrying the updated context. More importantly, the auth middleware records auth outcomes based on the response status even though it runs only on the protected route group; but the JWT validator middleware runs BEFORE it and may write the 401/403 and short-circuit — in that case next.ServeHTTP is still invoked here and the validator has already returned, so the recorder never sees the validator's own write, mis-attributing every denied request as 'granted'. — _Record the auth outcome based on the recorder status AFTER the full downstream chain has completed, and ensure the middleware ordering allows observing the validator's response; verify the validator's rejection actually passes through this recorder._
- ⚠ qr-preserves-behavior (`pkg/telemetry/telemetry.go`): The metric name 'http.server.request.duration' and unit 's' are also produced by the existing go-chi-metrics / Prometheus endpoint stack and by otelhttp semantics; emitting a custom histogram under the reserved OTel semantic-convention name from a hand-rolled middleware risks duplicate/conflicting series when the app also exposes Prometheus metrics. — _Use the otelhttp middleware (as the wiring notes instruct) for standard http.server.* metrics rather than hand-emitting the reserved conventional metric names._
- ⚠ general (`pkg/telemetry/telemetry.go`): The tenant attribute is populated from the raw X-API-Key header value, which is unbounded/high-cardinality and can explode metric series (and leak secrets) on the http.server.request.by_tenant counter. — _Hash or bucket the API key, or map it to a known low-cardinality tenant identifier before using it as a metric attribute._
