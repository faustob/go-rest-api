**Auto-fixed during review (9):**
- general (`cmd/metrics_otel.go`): activeRequestsMiddleware calls chiRouteCtx(req) but no chiRouteCtx function is defined anywhere in the diff, so the package will not compile.
- qr-not-a-noop (`cmd/metrics_otel.go`): The meter and all instruments are created in package init() via otel.Meter(meterScope), which runs before main() calls setupOTelSDK(). Because Go's otel.Meter returns a snapshot bound at call time (not a lazily-resolving proxy like OTel-JS), these instruments bind to the no-op default MeterProvider that is active before SetMeterProvider is called, so none of the custom metrics are ever exported.
- qr-not-a-noop (`cmd/otel.go`): The MeterProvider is built with metric.NewMeterProvider(metric.WithResource(res)) but no metric reader/exporter (e.g. PeriodicReader with an OTLP metric exporter, or a Prometheus reader) is configured. A MeterProvider with no reader collects and exports nothing, so all custom OTel metrics are silently dropped.
- qr-preserves-behavior (`cmd/metrics_otel.go`): activeRequestsMiddleware wraps every response in statusCapturingWriter, which only re-implements Flush; it drops the http.Hijacker, io.ReaderFrom, and http.Pusher interfaces of the underlying ResponseWriter, breaking WebSocket upgrades and other handlers that type-assert those interfaces.
- general (`cmd/otel.go`): otel.SetTracerProvider / otel.SetMeterProvider do not panic when a provider is already set (they simply overwrite), so the recover()-based guards are dead code; more importantly this means the code always overwrites any agent-set provider rather than preserving it as the comment claims.
- qr-otel-api-signatures (`cmd/metrics_otel.go`): metric.Int64Counter(name) returns (Counter, error) — the error must be handled, not ignored.
- qr-duplicate-metric (`cmd/metrics_otel.go`): Metric name "noop" is created 2 times in this change (cmd/metrics_otel.go:180, cmd/metrics_otel.go:188). Duplicate instrument registrations under one name produce merged/duplicate streams (double-counting), or an export conflict if their kind/unit differ.
- qr-not-a-noop (`cmd/server.go`): activeRequestsMiddleware calls flowEntryCounter.Add / requestOutcomeCounter.Add etc., but these package-level variables are only assigned inside initMetrics(). If setupOTelSDK fails (e.g. exporter creation errors, which only logs a warning and continues), initMetrics() is still called so the instruments are created against the no-op provider — however if setupTelemetryMetrics ran after a nil provider the counters would still be non-nil. The genuine defect: initMetrics is invoked unconditionally, so this is fine.
- qr-preserves-behavior (`cmd/server.go`): activeRequestsMiddleware wraps the ResponseWriter with middleware.NewWrapResponseWriter, replacing the ResponseWriter seen by all downstream handlers/middleware. This can strip http.Flusher/http.Hijacker/io.ReaderFrom optional interfaces relied on by downstream handlers, changing existing streaming/flush behavior.

- ⛔ qr-preserves-behavior (`cmd/metrics_otel.go`:210): The middleware wraps the ResponseWriter with middleware.NewWrapResponseWriter but does not preserve http.Flusher/Hijacker/other optional interfaces beyond what WrapResponseWriter provides, and more critically it is inserted before middleware.Recoverer, so a panic in a downstream handler will propagate through this middleware; the deferred activeRequests.Add(-1) runs but the counter .Add calls after next.ServeHTTP are skipped, and no functional break — but the wrapped writer changes streaming/flush semantics for handlers that rely on the raw ResponseWriter.
